# Provenance and Reproducibility

## Strict phases

`scripts/run_training_plan.py` creates `artifacts/paper_final/strict/<phase>/provenance.json` before the first child process. The sidecar records:

- an immutable copy of the uncommitted Python source used by child jobs;
- SHA256 values for the plan, selected hyperparameters, datasets, and source tree;
- the Python/package and GPU environment, Git status, and a diff snapshot;
- a phase-level `provenance_id`.

The child command executes the copied `run.py`, while dataset paths remain relative to the repository root. Each manifest row records the provenance id, configuration hash, UTC start/end times, and source-tree hashes before and after the child process. A changed snapshot causes the job to fail. Resume is refused when the plan, selection file, dataset, or snapshot differs from the immutable sidecar.

`scripts/validate_training_phase.py` is the gate before a report: it expands the registered plan, checks exact coordinates (including features and channel dimensions) and all command-affecting configuration fields, verifies the phase artifact type (`training_complete.json` for validation-only selection and `metrics.npy` plus predictions for test phases), and binds the result to the manifest/provenance hashes. For a newly started phase, the validator and lambda selector also require their own live script hashes to match the immutable phase snapshot. `scripts/build_final_report.py` additionally reloads standardized/original metric arrays and per-channel artifacts, refusing stale or edited raw CSV values. When a plan declares `confirmation_contract`, the validator, final-report builder, and paper-statistics entry point all require the same approved launch binding and an in-phase archived sidecar; exploratory/legacy plans without that contract retain their historical entry points.

**Historical strict caveat:** the six `strict` phase-validation files record the validator/selector versions used when those phases were generated. The live scripts were hardened afterward, so rerunning the current live validator against a historical strict manifest can legitimately report a live-hash mismatch. Treat the frozen strict `phase_validation.json` and snapshot as read-only audit evidence; do not overwrite them. Any new validation or statistic must use the independent `artifacts/paper_final/corrected/` root and its own snapshot.

`compute_paper_statistics.py` is an analysis-side tool rather than a training input. Every `paper_statistics.json` records its SHA-256. The completed corrected selection snapshots intentionally predate this analysis tool and do not include it. The live runner now includes both the statistics and resource scripts in every newly created confirmatory snapshot, so those phases bind analysis code to the same provenance sidecar. Never treat an analysis hash as a replacement for training provenance.

The completed corrected selection JSON files also have `selected_hyperparameters.provenance.json` sidecars generated by `scripts/attest_selection.py`. These sidecars independently replay the validation-trajectory criterion and bind the selected mapping to the validated manifest and snapshot. They are explicitly marked `posthoc_verified` (and `publication_ready=false`); they document a completed selection without retroactively turning an already-launched phase into a launch-time gate.

Before a new selected-lambda confirmatory phase is created, `run_training_plan.py` requires the sidecar and performs the same replay again. It checks the registered selection root, plan/features, exact AutoCon model keys and finite candidate lambdas, validation coverage, artifact hashes, source snapshot, and sidecar fields. The verified binding is copied into the confirmatory phase provenance and contributes to its `provenance_id`. This is recorded as `binding_mode=prelaunch_replay_of_posthoc_attestation`: it is a strong input-integrity gate for the new phase, but the underlying selection remains labelled `posthoc_verified` rather than being described as an originally launch-time selection.

## Legacy phases

The earlier selection, confirmatory-core, and secondary-transfer raw artifacts were completed before the current evidence chain was available. They were moved to the system Trash during repository cleanup because they have no role in the registered plan. Readable diagnostic summaries remain under `docs/reports/archive/`; they must be labelled `legacy/unknown code provenance`, and the current strict validator and final report intentionally reject them. The registered plan writes fresh outputs under `artifacts/paper_final/strict/`; all six registered phases have now completed with validator-passing manifests. Their status and report links are recorded in [`strict-evidence-status.md`](../reports/strict-evidence-status.md).

## Interpretation boundary

The S and M core reports are seed-level ETT ablations, not claims of state-of-the-art forecasting. The strict plan includes plain PatchTST and TimesNet as external baselines and a registered multivariate evaluation, but broader modern baselines, parameter/FLOPs-matched comparisons, and independent human review remain necessary before submission-level claims. Weather and Exchange-Rate are secondary transfer data; National Illness remains exploratory because the source is weekly while the current loader uses step-based horizons.
