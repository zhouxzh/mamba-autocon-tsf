# MambaACF Sidecar Replay Audit

This note is the human-review addendum for
`mamba_acf_sidecar_replay_20260831`. It deliberately does not modify the
registered plan: the plan SHA-256 is embedded in all three phase provenance
records and changing the JSON would invalidate those immutable records.

## What the 18 runs establish

- The three phases contain 18 successful jobs, each with a complete
  `acf_prior.npz` and a SHA-256 binding in `config.json`.
- A current strict, read-only **sidecar schema/loading** audit passed all 18
  sidecars. It checks schema fields, positive unique lags, compact width,
  full-table width, selected-lag bounds, and `acf_full_values[:, lags] ==
  acf_values`; it is not a validation of end-to-end representation causality.
- The stored test metrics were produced during the training process after the
  train-only prior was fitted. The sidecar was persisted afterward. No metric
  in this screen was generated by a later `is_training=0` evaluation that
  loaded the sidecar.

## Source boundary

The phase provenance records bind the training jobs to source tree
`65be5472042697fa189e8ff35017ee16da18999666ebe5b51828de5afc66b3c6`. The live
tree now differs in eleven captured files:

`data_provider/data_factory.py`, `data_provider/samplers.py`,
`exp/exp_long_term_forecasting_with_AutoCon.py`,
`exp/exp_long_term_forecasting_with_mamba.py`, `layers/losses.py`,
`models/MambaACF.py`, `run.py`, `scripts/benchmark_model_resources.py`,
`scripts/run_training_plan.py`, `scripts/validate_training_phase.py`, and
`tests/test_confirmation_statistics.py`.

The historical source snapshot remains the authority for interpreting the
training numbers; current working-tree hashes are recorded only as replay
runtime metadata and are not substituted into the immutable provenance.

The wrapper change includes canonical lag ordering. The selected lag set is
unchanged, but ordering can affect coefficient/feature construction and is a
training-path change. Consequently the numeric table is a
**provenance-snapshot training result**, followed by a current-tree contract
audit; it is not a current-tree rerun.

The existing `phase_validation.json` files remain valid for the exploratory
plan they were created under. That plan has no `confirmation_contract`, so
`valid=true` is not a strict confirmation gate. The separate 18/18 strict
sidecar audit does not upgrade the screen to confirmatory evidence.

## Standalone replay result

The isolated report
[`replay_report.md`](../../artifacts/exploratory/mamba_acf_sidecar_standalone_replay_20260831_audit/replay_report.md)
does exactly this for all 18 jobs: each job loads the checkpoint and
`acf_prior.npz` with `is_training=0` in a separate output directory, records
the resolved metadata, and compares stream metrics with the training-time
record. The frozen [`replay_manifest.json`](../../artifacts/exploratory/mamba_acf_sidecar_standalone_replay_20260831_audit/replay_manifest.json)
contains input hashes, commands, environment and tolerances; the companion
`replay_results.jsonl` is appended after each job. All 18 jobs passed both
the contract and metric checks, all sidecar hashes matched, and the maximum
absolute differences were `3.3e-9` for MSE and `2.2e-9` for MAE.

All 18 jobs report the same benign normalization: the historical effective lag
order is `[96, 72, 120]`, while the live loader resolves `[72, 96, 120]`.
The canonical lag sets are identical, so this is recorded as
`lag_order_normalized=true`, not as a contract failure. It remains a source
drift to disclose because ordering can affect feature construction during
training.

This is an evaluation-path replay against historical checkpoints. A new
current-tree training result would still require a newly captured source
snapshot and a new output root; the existing immutable phase roots remain
unchanged.

The replay can be regenerated with the following command in the `mamba`
environment (the output root must be empty):

```bash
PYTHONPATH=. conda run --no-capture-output -n mamba python scripts/replay_mamba_acf_sidecars.py \
  --source-root artifacts/paper_final/mamba_acf_sidecar_replay_20260831 \
  --output-root artifacts/exploratory/mamba_acf_sidecar_standalone_replay_20260831_audit \
  --timeout 300
```

The screen remains exploratory (`n=3` seeds per dataset, H96) and cannot
support a publication claim about a stable accuracy or speed advantage.

## 2026-09-02 data-bound replay

The compatibility report above predates the stricter input-binding checks. A
new read-only replay was run against the three live-screen phase roots and
written to [`mamba_acf_data_bound_replay_20260902_v2`](../../artifacts/exploratory/mamba_acf_data_bound_replay_20260902_v2/).
All `18/18` jobs passed the contract and metric checks. The replay used the
current loader with `is_training=0`; it did not retrain or alter any source
phase.

Before each subprocess, schema-4 `replay_manifest.json` freezes and checks:

- the phase `manifest`, `provenance`, and `phase_validation` hashes;
- the immutable source snapshot and registered plan hash;
- the actual dataset SHA-256 against the phase provenance;
- every declared source artifact (`config.json`, `acf_prior.npz`, checkpoint,
  and logged result arrays); and
- the job/config identity (setting, plan job id, dataset, executable model
  alias, seed, and sidecar hash).

The manifest and report also pin the replay tool path and SHA-256, so the
loader implementation that generated the audit is recoverable alongside the
live `run.py` hash.

The copied inputs are hashed again before execution. The resulting
`replay_report.json` records `18/18` contract passes, `18/18` metric matches,
and no non-OK records. The maximum absolute differences were `8.34e-10` for
MSE and `3.36e-10` for MAE. This is stronger data-binding evidence for the
evaluation path, but it does not upgrade the historical training screen to a
current-tree or confirmatory result.

## Current validator boundary

Running the current `validate_training_phase.py` in read-only mode against the
same historical roots gives a different answer from the replay: plain and
memory phases have no record-level errors but are marked invalid because
`run_training_plan.py` has changed since their immutable snapshot. The six
relation records additionally lack the newly required sampler metadata and
realised lag-pair telemetry (`requested/effective/reason`, selected-lag
support, and per-lag counts/exposure). Those old logs are retained unchanged;
they must be rerun under the repaired contract before any strict relation
confirmation aggregate. The replay therefore establishes checkpoint loading
and data/artifact identity, not compliance of the old training logs with the
new sampler contract.

The exact read-only validator outputs are archived in
[`mamba_acf_live_screen_current_validator_audit_20260902`](../../artifacts/exploratory/mamba_acf_live_screen_current_validator_audit_20260902/).
